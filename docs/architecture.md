━━━ IRREVERSIBLE DECISIONS (ADRs) ━━━

ADR-001: Database choice
Chosen: SQLite via rusqlite (Rust-side, embedded)
Alternative considered: IndexedDB (browser-side) or PostgreSQL (cloud). IndexedDB is too limited for complex queries (conversation search, tool registries, settings). PostgreSQL requires external setup — violates zero-config principle.
Rationale: SQLite is embedded (no install, no config, no process to manage), fast for single-user workloads, supports full SQL for conversation search and tool registries, and rusqlite provides safe Rust bindings. Database file lives in the app's data directory. Backups are trivial (copy a file). Migrations run automatically on app start via Rust migrations.
Revisit trigger: If the app needs cross-device sync (mobile companion apps) — then consider a sync layer. SQLite stays as the local DB; sync is a layer on top.

ADR-002: Frontend-backend communication
Chosen: Tauri commands (IPC via `#[tauri::command]`)
Alternative considered: REST API (localhost HTTP server) or WebSocket. REST on localhost adds an HTTP server dependency that the OS firewall may block. WebSocket is overkill for request-response patterns.
Rationale: Tauri commands are the native IPC mechanism. Frontend calls `invoke("command_name", { args })` and receives a typed response. The Rust backend registers commands with `#[tauri::command]`. This is serialized via JSON over the Tauri IPC bridge. No ports to configure, no HTTP parsing overhead. Streaming responses (LLM tokens) use Tauri events (`emit`) for the token stream, with the initial `invoke` returning a stream ID.
Revisit trigger: If performance becomes bottlenecked (JSON serialization of large payloads), consider a binary protocol. Unlikely for chat-sized messages.

ADR-003: LLM inference engine
Chosen: llama.cpp via Rust bindings (llama-cpp-2 or candle)
Alternative considered: OnnxRuntime, burn, or invoking llama.cpp as a subprocess. OnnxRuntime lacks the GGUF model ecosystem. Burn is immature for LLMs. Subprocess adds latency and process management complexity.
Rationale: llama.cpp is the industry standard for local LLM inference with GGUF models. The Rust bindings provide a safe, performant interface to the C++ library. The massive GGUF model ecosystem (HuggingFace) gives users thousands of model choices. GPU acceleration (CUDA, Metal, Vulkan) is built in. The Rust binding allows Ouroboros to detect hardware and select the optimal backend at compile time.
Revisit trigger: If llama.cpp maintenance burden exceeds value (breaking API changes, build issues per platform), evaluate mistral.rs or a pure Rust solution. Currently llama.cpp is too dominant to justify switching.

ADR-004: Sandboxed tool execution
Chosen: Rust-based process sandboxing with OS-level isolation + explicit permission model
Alternative considered: Docker containers (OpenClaw's approach) or Wasm/WASI sandboxing. Docker requires Docker installation — violates zero-config. Wasm/WASI is too limited for real OS operations (file system access, running native binaries).
Rationale: Tauri/Rust provides direct OS access with fine-grained control. The sandbox model uses: (1) a separate child process spawned with restricted permissions, (2) file system access limited to an allowed directory list, (3) network access disabled by default (opt-in per command), (4) command execution restricted to an allowlist built from the tool registry, (5) a permission prompt shown in the UI before any execution. The Rust backend enforces the sandbox at the OS level — the UI permission dialog is the user-facing layer, not the enforcement layer.
Revisit trigger: If a sandbox escape vulnerability is discovered. The current design assumes OS-level process isolation is sufficient. An RCE vulnerability in the sandbox implementation would require revisiting the architecture fundamentally.

ADR-005: Storage encryption for API keys
Chosen: AES-256-GCM encryption with a device-derived key (keyring or OS credential store)
Alternative considered: Plain-text config file (security risk), external vault (complexity), or no persistent key storage (user must re-enter keys each session).
Rationale: API keys for BYOK providers must be stored locally but encrypted. The encryption key is derived from the OS credential store (Windows Credential Manager, macOS Keychain, Linux libsecret). If the credential store is unavailable, fall back to a machine-derived key with a warning. Keys are never sent to any server. Encryption/decryption happens in the Rust backend; the frontend never sees raw keys.
Revisit trigger: If a major provider mandates OAuth-only (no API key) access. Currently OpenAI, Anthropic, and Google all support API keys.

ADR-006: State management (frontend)
Chosen: React Context + React Query (TanStack Query) for server state
Alternative considered: Zustand, Redux, Jotai, or signals-based approach. Redux is over-engineered for a single-user chat app. Zustand is fine but duplicates TanStack Query's caching layer unnecessarily.
Rationale: The primary "server state" is conversation/message data from the Tauri backend. TanStack Query handles caching, background refetch, and optimistic updates natively. React Context handles UI state (bubble position, chat visibility, input focus). This split prevents stale caches and keeps the state architecture simple. Tauri command invocations are the "fetcher" functions for TanStack Query.
Revisit trigger: If the app grows beyond 10-15 screens and Context becomes unwieldy. Zustand would be the likely replacement — but v1 doesn't justify it.

━━━ DATABASE SCHEMA ━━━

All tables in SQLite, managed via Rust migration files.

Table: conversations
  id              TEXT PRIMARY KEY (UUID v4)
  title           TEXT NOT NULL DEFAULT 'New conversation'
  model_id        TEXT NOT NULL (e.g. 'local/llama-3.2-3b', 'cloud/openai/gpt-4o')
  created_at      TEXT NOT NULL (ISO 8601)
  updated_at      TEXT NOT NULL (ISO 8601)
  Indexes:
    idx_conversations_updated ON (updated_at DESC) — conversation list sorted by recency

Table: messages
  id              TEXT PRIMARY KEY (UUID v4)
  conversation_id TEXT NOT NULL → conversations.id (FK, CASCADE DELETE)
  role            TEXT NOT NULL CHECK (role IN ('user', 'assistant', 'system', 'tool'))
  content         TEXT NOT NULL
  tool_calls_json TEXT (JSON array of tool call objects, nullable)
  token_count     INTEGER (estimated, for context window management)
  created_at      TEXT NOT NULL (ISO 8601)
  Indexes:
    idx_messages_conversation ON (conversation_id, created_at ASC) — load messages in order
    idx_messages_created ON (created_at) — for "search all messages" queries

Table: api_keys
  id              TEXT PRIMARY KEY (UUID v4)
  provider        TEXT NOT NULL (e.g. 'openai', 'anthropic', 'google', 'kie_ai', 'pollinations')
  label           TEXT (user-provided name, e.g. "My OpenAI key")

  created_at      TEXT NOT NULL (ISO 8601)

  key             TEXT PRIMARY KEY

  id              TEXT PRIMARY KEY (UUID v4)

━━━ AUTH FLOW ━━━

Session strategy: Local device profile — no login required.

The app generates a device ID on first launch (UUID v4, stored in SQLite settings).
This ID is the "user" — there is no username, password, or cloud account for v1.

For BYOK cloud models:
  1. User enters API key in Settings → Rust backend encrypts with AES-256-GCM →
     stored in `api_keys` table.
  2. When selecting a cloud model, the backend decrypts the key, attaches it to
     the provider request, and never exposes the raw key to the frontend.
  3. For OAuth providers: the Rust backend opens the system browser for the OAuth
     flow. The redirect URI is intercepted by the Tauri app via a custom protocol
     handler (ouroboros://callback). The token is encrypted and stored.

For paid tier (v2):
  A web service handles account management, license validation, and subscription
  state. The desktop app communicates with this service via a short-lived token
  obtained through email verification or device pairing. This is NOT in v1.

Middleware: Not applicable — this is a desktop app, not a web server. Every
Tauri command has access to the app state. There is no "auth middleware" because
there is no multi-user request context. The single device is the single user.

━━━ DATA FLOW ━━━

The core interaction loop:

1. User clicks bubble → Bubble animates into bottom-screen input bar (150ms, ease.enter)
2. User types message, presses Enter → Frontend calls `invoke("send_message", { message })`
3. Rust backend:
   a. Creates or appends to conversation in SQLite
   b. Inserts user message
   c. Loads conversation context from SQLite
   d. If local model: loads GGUF model (cached in memory), runs inference via llama.cpp
      If cloud model: fetches API key from encrypted store, calls provider API
   e. Streams tokens via `app.emit("chat:token", { conversation_id, token, index })`
4. Frontend listens on `chat:token` event → StreamingText component renders tokens in real-time
5. On completion: Rust backend inserts assistant message into SQLite, emits `chat:done`
6. Frontend updates message list, scrolls to bottom

Tool execution flow:

1. Assistant response includes a tool call suggestion
2. Frontend renders tool call as an inline card with "Run" button
3. User clicks "Run" → Frontend calls `invoke("execute_tool", { tool_name, input })`
4. Rust backend:
   a. Checks if tool is enabled in tool_registry
   b. Evaluates permission: if default is "ask" → returns to frontend with "ask" status
   c. Frontend shows PermissionDialog
   d. User approves → Frontend calls `invoke("execute_tool", { ... })` with approval flag
   e. Rust spawns sandboxed process, executes command, captures stdout/stderr
   f. Returns result to frontend
   g. Frontend renders ExecutionResult in chat
5. If permission default is "deny" → refused. User can change permission defaults in Settings.

# Ouroboros — AGENTS.md

## What is this?
Ouroboros is a local-first desktop AI assistant built with Tauri v2. It lives as a
floating bubble overlay on the user's desktop, providing AI chat and OS-level tool
execution. It aims to be the "operating system's native Copilot — with self-evolving
intelligence."

## Stack
- **Desktop framework:** Tauri v2 (Rust backend, React 19 frontend)
- **UI:** React 19, Tailwind CSS v4, TypeScript strict
- **Database:** SQLite via rusqlite (Rust-side, embedded)
- **LLM inference:** llama.cpp via Rust bindings
- **Tests:** Vitest (unit/component), Playwright (E2E), cargo test (Rust)
- **Package manager:** pnpm
- **Target platforms:** Windows (primary focus), macOS, Linux

## How to run locally
```bash
# Prerequisites: Rust, Node.js 22+, pnpm
pnpm install
pnpm tauri dev     # Development with hot-reload
pnpm tauri build   # Production build
```

## How to run tests
```bash
cargo test                    # Rust tests
pnpm test                     # Vitest (frontend unit/component)
pnpm test:e2e                 # Playwright E2E tests
```

## Conventions
- **Commits:** Conventional commits — feat:, fix:, test:, docs:, refactor:, chore:
- **Branches:** feat/feature-name per slice, squash merge
- **Tags:** ophidian/slice-N after each merge
- **TypeScript:** strict mode, no `any` without justification, explicit return types
- **Rust:** standard Rust conventions, `cargo fmt` + `cargo clippy` enforced
- **Visual values:** ALL colors, spacing, radii, shadows, fonts reference design-system.md tokens. No hex codes in components, no ad-hoc spacing.
- **Copy:** ALL user-facing text uses keys from docs/copy-v1.md. No inline strings in components.
- **States:** Every interactive component implements loading, empty, error, and success states.

## Key architectural patterns
- Frontend calls Rust backend via Tauri `invoke()` commands (not REST)
- Streaming responses use Tauri events (`emit`/`listen`)
- SQLite database lives in the app data directory, auto-migrates on startup
- API keys encrypted via AES-256-GCM, key from OS credential store
- Sandboxed tool execution via OS-level process isolation (not Docker)
