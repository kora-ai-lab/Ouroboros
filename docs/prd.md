PRD — Ouroboros v1.0
Generated by Ophidian · Phase 2

━━━ VISION ━━━
User outcome (1 sentence): Summon an AI assistant from a floating bubble on your desktop that answers questions and executes tasks on your computer — without opening a browser tab, launching a terminal, or touching a config file.

━━━ 80/20 PRODUCT THESIS ━━━
The 20% of features that deliver 80% of user value:

1. **P0 — Floating bubble UI + chat container** — blocks everything else. Build first. The structural differentiator: a persistent, draggable bubble that's always one click away from any app. Expands into a bottom-screen input area; grows into a full chat when the user needs more interaction. No window management, no Alt-Tab, no context switch. This is the feature that makes every other feature accessible.

2. **P0 — Local AI inference engine** — enables the core loop. Private, offline, zero-latency chat. Ships with a small, fast default model pre-downloaded on install. Detects the user's GPU (CUDA, Metal, Vulkan) and auto-configures for best performance. Cloud model fallback is one toggle away — but the default experience is local, private, and instant. This is the trust anchor.

3. **P0 — Sandboxed tool execution engine** — minimum for the product to feel like a product, not a demo. The assistant can read/write files, run terminal commands, and execute scripts — all inside a sandbox with explicit user permission. The permission model defaults to "ask every time" for destructive actions, "allow once" for reads. No Docker, no config, no terminal — the sandbox is invisible to the user. This is what makes Ouroboros an agent, not a chatbot.

Everything else is P1 or deferred. Total P0 features: exactly 3.

━━━ PERSONAS ━━━

Primary persona:
  Who: A professional, creator, or everyday computer user (not a developer) who uses AI daily — currently via ChatGPT/Claude in a browser tab. They're on Windows or Mac, technically capable enough to install an app, but they won't edit a config file and they don't know what a terminal is. They want answers and action without breaking flow.
  Current pain (verbatim from research): "I just want to ask a question or tell something to happen without stopping what I'm doing."
  JTBD: "When I'm working on my computer and need an answer, a file edited, or a task automated, I want to summon my assistant instantly without leaving my current app, so that I can stay in flow and get the result without breaking context."
  Their "aha moment": When they type their first request and the assistant responds — and then executes the action on their machine — without them having opened a single browser tab, terminal window, or config file. The reaction is "it just works."

Secondary persona:
  Who: A power user or developer who knows what OpenClaw is but wants something simpler, or who wants a cross-platform option, or who wants a polished GUI instead of CLI bots. They're on Windows, Mac, or Linux. They'll push the execution engine to its limits.
  JTBD: "When I need to automate a complex workflow or build a custom tool, I want my assistant to handle the execution while I stay in my flow, so that I don't have to context-switch between terminal, browser, and IDE."

Note: The secondary persona is not the design target. The primary persona (non-technical user) dictates every UX decision. If the product works for them, it works for developers too. The reverse is not true.

━━━ FEATURE MANIFEST ━━━

FEATURE-001: App Shell + Floating Bubble
P0/P1: P0
Why this feature: The bubble is the product's face. It must exist before any other feature can be accessed. It's also the primary differentiator — the thing users notice and ask about.
Depends on: none
Estimated effort: L (cross-platform Tauri window management, overlay rendering, drag behavior, system tray integration, auto-start)
Key risk: OS-level overlay windows behave differently across Windows, macOS, and Linux. Tauri's window management API may need per-platform workarounds. The bubble must survive fullscreen apps, multiple monitors, and different DPI scales.

FEATURE-002: Chat Interface
P0/P1: P0
Why this feature: The user needs somewhere to type and see responses. The chat interface starts as a compact input bar at the bottom of the screen (activated from the bubble), then expands into a full chat container for longer interactions.
Depends on: FEATURE-001
Estimated effort: L (streaming text rendering, markdown support, code blocks, message history, input bar → full chat transition animation, scroll behavior)
Key risk: Streaming LLM output requires smooth, non-janky text rendering at high token rates. Markdown rendering must be fast and secure (no XSS). The input-bar-to-chat transition must feel natural, not janky.

FEATURE-003: Local LLM Inference
P0/P1: P0
Why this feature: Private, offline AI is the trust anchor and the free tier's core value. A user who doesn't trust cloud AI or doesn't want to pay should still get a fast, useful assistant.
Depends on: none (runs in Rust backend, independent of the UI)
Estimated effort: XL (llama.cpp integration, model download management, GPU detection + optimization, prompt templating, context management, performance tuning per platform)
Key risk: llama.cpp's build pipeline differs per platform (CUDA on Windows, Metal on macOS, Vulkan/CPU on Linux). The model download UX must handle multi-GB files with resume support. First-run experience on slow hardware could damage perception.

FEATURE-004: Tool Execution Engine
P0/P1: P0
Why this feature: This is what separates Ouroboros from every chat-only assistant. The ability to read/write files, run commands, and execute scripts on the user's machine is the core-loop enabler.
Depends on: FEATURE-001 (needs the app shell for permission dialogs)
Estimated effort: L (process sandboxing via Rust, permission model implementation, file system guardrails, command allowlisting/denylisting, undo capability for file writes)
Key risk: Sandbox escape vulnerabilities are existential. Every command path must be audited. The permission UX must be fast (not interruptive) while remaining safe. A single "assistant deleted my files" incident kills the product.

FEATURE-005: Model Provider Integration (BYOK + Built-in)
P0/P1: P1
Why this feature: Local AI is the default, but users who want cloud models (Claude, GPT, etc.) need a path to use them. BYOK keeps Ouroboros agnostic and avoids being a middleman.
Depends on: FEATURE-002 (chat interface needed to display responses), FEATURE-003 (model management infrastructure)
Estimated effort: M (OAuth flows for OpenAI, Anthropic, Google; API key vault with encryption; model switching UI; streaming adapter layer)
Key risk: Each provider's streaming API has quirks. OAuth token management across providers is fiddly. Users will blame Ouroboros for provider API errors or rate limits.

FEATURE-006: Conversation Memory & History
P0/P1: P1
Why this feature: The assistant must remember past conversations and context across sessions. Without memory, it's a stateless chatbot — every interaction starts from zero. This kills retention.
Depends on: FEATURE-002 (chat interface), FEATURE-003 (inference integration)
Estimated effort: M (SQLite conversation store, conversation list UI, context window management, semantic search for past conversations)
Key risk: Context window limits mean the assistant can't load all history. Summarization/compaction must work reliably or users lose important context. Storage must stay small despite years of conversations.

FEATURE-007: Onboarding Flow
P0/P1: P1
Why this feature: The first 2 minutes determine activation or uninstall. The onboarding must get the user to the "first response" milestone before they've read any instructions. This directly addresses the #1 objection: "it looks complicated."
Depends on: FEATURE-001 (bubble), FEATURE-002 (chat), FEATURE-003 (local inference)
Estimated effort: M (guided first-run flow, model pre-selection based on hardware, sample prompts, progress indicators, skip/default options for everything)
Key risk: Over-engineering the onboarding creates a wizard that users click through without reading. Under-engineering it leaves them confused. The sweet spot: show the bubble, prompt "type anything," demonstrate the result.

FEATURE-008: Landing Page + Distribution
P0/P1: P1
Why this feature: Users need to discover and download the product. The landing page is also the first test of copy hypotheses and brand positioning.
Depends on: none (can be built in parallel with everything)
Estimated effort: M (Next.js/Astro landing page, download flow with OS detection, product screenshots/demo video, social proof section, /alternatives/openclaw page)
Key risk: Landing page copy is hypotheses until launch data proves or disproves it. Don't spend 2 weeks polishing copy that may be rewritten entirely after D+7 user feedback.

━━━ OUT OF SCOPE (V1) ━━━
→ Cloud model orchestration (paid tier) — deferred because local AI + tool execution alone proves the value proposition. Paid tier monetization is v2, not v1 MVP function.
→ Self-evolving tool creation (recursive architecture) — deferred because the sandboxed execution engine is the prerequisite. Ship the engine in v1; the recursive tool-builder IS v2's killer feature.
→ Multimodal generation (image/video) — deferred because text + action on the user's machine is the 80/20 core. Media is v2 expansion.
→ Voice (TTS/STT) — deferred because text chat is the universal interface. Voice is a v2 differentiator once the text experience is solid.
→ Mobile companion apps (iOS/Android) — deferred because desktop is the platform. Mobile is v2 expansion.
→ Enterprise licensing — deferred until v1 proves product-market fit for individuals. Build for one user first.
→ Plugin/extension marketplace — deferred because OpenClaw has a massive head start on extensions. Ouroboros's execution engine is the differentiator, not the extension count.
→ Local embeddings / vector search for memory — deferred because conversation-level history (SQLite) is sufficient for v1. The "recall from 20 years ago" capability needs vector search, which is a v2 infrastructure upgrade.

━━━ DATA THAT WILL CHANGE OUR MIND ━━━

Signal 1: D+1 retention < 30%
→ The product isn't sticky. Before adding features, investigate: Are users reaching the aha moment? Is the local model too slow on their hardware? Is the bubble annoying them? Fix the fundamental experience — don't patch it with more features.

Signal 2: 90%+ of messages are plain chat (zero tool executions)
→ The execution engine isn't being discovered or isn't trusted. The assistant is failing to suggest actions, or users don't know it CAN do things. Fix: make tool suggestions more prominent in the chat UI, simplify the permission UX, add a "suggested actions" onboarding step.

Signal 3: Uninstall rate > 10% within D+7
→ Something is fundamentally broken. Top suspects: local inference too slow on consumer hardware (the assistant feels sluggish), the bubble is perceived as intrusive/bothersome, or a crash/data-loss event damaged trust. Stop feature development and fix the root cause.

Signal 4: 80%+ of users immediately configure cloud models (never use local)
→ The local AI value proposition isn't compelling. Users either don't trust it, find it too slow, or don't understand it exists. Either improve local model performance/quality, or pivot the positioning to "cloud-first with optional local."

Signal 5: NPS < 20 from first 50 users despite high retention
→ Users are using it reluctantly (it's useful but unpleasant). This is a UX death sentence — the assistant works but feels like a chore. Redesign the interaction model. High retention + low satisfaction = a product people need but resent.
