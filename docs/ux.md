## SCREEN 0: DESKTOP STATE (Bubble Only)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SCREEN: Floating Bubble — Route: N/A (overlay, always visible)

━━━ PURPOSE ━━━
When the user is working on any application and hasn't summoned the assistant, the bubble is the persistent visual anchor — it says "I'm here when you need me" without interrupting. Clicking it activates the assistant.

━━━ VISUAL HIERARCHY ━━━
Priority order:
  1. Bubble glow (warm amber halo) — the first thing the eye notices on the desktop
  2. Bubble surface (translucent glass circle with amber tint)
  3. Interior icon (subtle, minimalist mark — an Ouroboros symbol or simple dot)
  4. Notification badge (only when there's an unanswered message — red dot)

How achieved:
  → Size: bubble is 44px diameter (compact, not dominant)
  → Color: amber glow is the only warm element on a typical cold desktop
  → Position: bottom-right corner by default (space.6 from right + bottom edge). User can drag to any position.
  → Whitespace: the bubble floats alone — no adjacent UI elements
  → Typography: none (icon only at rest state)

━━━ COMPOSITIONAL INTENT ━━━
The bubble is a single, centered object. It's deliberately small (44px) — it should not compete with the user's work. The glass treatment (semi-transparent surface, subtle border, soft glow) makes it feel physical — like a glass marble sitting on the desktop, not a pixel rectangle. The warm amber color is the single intentional brand signal on the entire screen.

The bubble drags smoothly — it shouldn't snap to a grid or feel laggy. It should feel like a physical object being moved. Mouse cursor changes to "grab" on hover, "grabbing" during drag.

On dual monitors: the bubble stays on the primary monitor. User can drag it to any monitor.

└─ Bubble
    ├─ Glass surface (circular, semi-transparent, amber-tinted)
    ├─ Glow halo (brand.400 at 15% opacity, blurred shadow)
    ├─ Interior icon (Lucide icon, icon.lg or icon.xl, text.on-brand or icon.primary)
    └─ Notification badge (red dot, 8px diameter, top-right corner) — conditional

━━━ STATES ━━━

LOADING STATE (startup):
  Visual: Bubble fades in with a soft pulse (opacity 0 → 1 over 400ms, ease.enter). Interior icon glows briefly. This is the app startup — the bubble is the first thing the user sees.
  Duration: < 1s. The app boots into a ready state quickly.

EMPTY STATE (no conversations yet):
  Visual: Standard bubble appearance. No badge. No indication of "newness" — the bubble doesn't change based on whether you've used it.
  Copy: None at rest.

ERROR STATE (LLM failed to load, or app crashed):
  Visual: Bubble surface dims to neutral.700 (25% opacity). Glow turns cool/neutral (no amber). Interior icon changes to a warning indicator (exclamation mark, icon.sm, status.error).
  Recovery: User clicks bubble → bubble expands to input bar but shows "Something went wrong. [Restart Ouroboros]" above the input. The input is disabled until the user restarts or the backend recovers.
  Edge case: If the backend can't recover, the bubble shows the error state until app restart.

SUCCESS STATE (normal idle):
  Visual: Standard bubble — warm amber glow, translucent glass, interior icon. Subtle pulsing animation on the glow every 6-8 seconds (slow, breathing-like) to indicate "alive and listening" without being distracting.

━━━ INTERACTIONS ━━━

Hover: Bubble scales to 1.05x (75ms, ease.default). Glow intensifies slightly. Cursor: pointer.
Click: Bubble shrinks to 0.95x then expands to input bar (300ms total: 75ms press + 225ms transition). The bubble itself fades out as the input bar fades in. Cursor auto-focuses to the input field.
Right-click: Context menu with: "New conversation", "Settings", "Hide bubble" (dismisses to system tray), "Quit Ouroboros".
Drag: Bubble follows cursor at 1:1. Release positions the bubble at the drop point. Position saved to settings.

Keyboard: When bubble is focused (clicked), pressing any alphanumeric key opens the input bar with that character pre-typed.

━━━ ACCESSIBILITY ━━━
Focus order: N/A at rest (not in tab order of other applications).
ARIA: Bubble has role="button", aria-label="Open Ouroboros assistant".
Keyboard: Bubble can be activated via a global hotkey (configurable, default: Alt+Space).
Screen reader: Announces "Ouroboros assistant — press Alt+Space or click to open."
Contrast: Bubble glow visible against all desktop backgrounds. Interior icon meets contrast minimums against the bubble surface.

━━━ RESPONSIVE BEHAVIOR ━━━
The bubble is always 44px. Size does not change across displays or DPI scales. On high-DPI displays, the glass surface renders at native resolution (no pixelation). The bubble positions relative to screen edges at all screen sizes.

## SCREEN 1: INPUT BAR
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SCREEN: Input Bar — Route: N/A (overlay, bottom of screen)

━━━ PURPOSE ━━━
When the user summons the assistant but wants a quick answer (not a full conversation), the input bar provides a compact, single-line interface at the bottom of the screen. The user types, presses Enter, and the response appears above the bar. This is the "quick ask" mode — the most common interaction.

━━━ VISUAL HIERARCHY ━━━
Priority order:
  1. Input field (dominant, centered, auto-focused) — the user's first action point
  2. Send button or submit hint (brand-colored, right-aligned)
  3. Model indicator (small label showing active model, left of input or above)
  4. Response area (above the bar, semi-transparent, appears on response arrival)

How achieved:
  → Size: bar is 64px tall, spans screen width with 24px horizontal padding
  → Color: bg.input background, brand border on focus
  → Position: anchored to bottom of screen, slides up on activation
  → Whitespace: generous padding around input, response appears above with breathing room

━━━ COMPOSITIONAL INTENT ━━━
The input bar occupies the full width of the screen at the bottom — not a small floating rectangle. This anchors the UI to the bottom edge, creating a structural relationship with the desktop. The wide bar signals "type anything — I'm ready." The response area above the bar is semi-transparent with a blurred backdrop, letting the user's application show through — the user is still "in" their work.

On activation from the bubble: the bubble scales down and fades out while the input bar slides up from the bottom edge (250ms, ease.enter). The input field auto-focuses. If the user activated from a global hotkey, the current application's focused element is remembered and restored when the bar closes.

└─ InputBar (fixed, bottom of screen, 64px height)
    ├─ ResponsePreview (conditional, above bar, semi-transparent bg.surface with backdrop-blur)
    │   ├─ Streaming text (body, text.primary)
    │   └─ Expand prompt ("Open full chat" link, text.link)
    ├─ BarSurface (bg.input, radius.lg top-left + top-right, radius.none bottom)
    │   ├─ ModelIndicator (label-sm, text.tertiary, left-aligned)
    │   ├─ InputField (body, text.primary, flex-1)
    │   └─ SubmitButton (brand-colored icon, icon.md)
    └─ Suggestions (conditional, above bar, horizontal chip list — only on empty input)

━━━ STATES ━━━

LOADING STATE (sending message, waiting for response):
  Visual: Input field stays visible but shows a subtle shimmer animation. Submit button changes to a stop icon (if streaming can be cancelled) or a subtle pulse animation.
  Response area: Shows skeleton lines (2-3 lines of shimmering blocks matching the expected response width). After 1s, a "Thinking..." label appears (label-sm, text.tertiary) with a subtle animated dot sequence.
  Duration strategy:
    - < 200ms: no loading indicator (perceived as instant)
    - 200ms-1s: skeleton lines appear
    - 1s+: skeleton + "Thinking..." label with animated dots
    - 5s+: "Still working..." label + option to cancel
  Copy: [chat.loading.thinking], [chat.loading.still_working]

EMPTY STATE (first time opening):
  Visual: Input bar with subtle placeholder text. Suggestion chips appear above the bar (3 example prompts to help the user understand what to ask).
  Copy: Input placeholder: [chat.input.placeholder]. Suggestions: [chat.suggestions.example_1], [chat.suggestions.example_2], [chat.suggestions.example_3].
  Psychological strategy: The suggestions demonstrate the assistant's capabilities — they're not generic "what can you help with?" but specific tasks the assistant can execute. This teaches the user the product's power through suggestion, not instruction.

ERROR STATE (message failed to send, or LLM error):
  Visual: Input field border turns border.error. A small error message appears above the bar (body-sm, status.error) with a specific reason and recovery action.
  Message: [error.chat.network] or [error.chat.model_unavailable] — specific, not "something went wrong."
  Recovery: Retry button appears next to the error message. User can edit the message and resend.
  Edge case: If the error happens mid-stream (partial response already shown): the partial text stays visible but is grayed out, and the error message appears below it explaining that the response was incomplete.

SUCCESS STATE (message sent, response received):
  Visual: ResponsePreview shows the full streaming text with smooth token-by-token rendering. At the end of the response, the expand prompt appears: "Open full chat →" (label, text.link).
  If the response includes a tool call: a compact tool result card appears in the preview area instead of plain text, with a "Run" button.
  Micro-interactions: Each new token animates in (subtle 50ms fade-in per token chunk). The scroll area auto-scrolls to the latest content.

━━━ INTERACTIONS ━━━

Type: Characters appear in the input field with instant feedback.
Enter: Message sends. Input field clears. Loading state begins.
Shift+Enter: New line in the input (for multi-line requests).
Escape: Closes the input bar → bubble reappears (200ms, ease.exit).
Click "Open full chat": Input bar expands into Chat Container (250ms, ease.enter).
Click response area: Also expands to Chat Container.
Click outside bar: Closes the bar → bubble reappears. Input text is preserved if the user reopens within 30 seconds.

━━━ ACCESSIBILITY ━━━
Focus order: Input field auto-focused on open. Tab moves to Submit, then suggestions (if visible).
ARIA: Input has aria-label="Ask anything". Submit button has aria-label="Send message".
Keyboard shortcuts: Enter to send, Shift+Enter for newline, Escape to close.
Screen reader: Announces "Input ready — type your request" on open. Announces "Response received" when streaming completes.
Contrast: Input text meets 4.5:1 ratio against bg.input. Placeholder meets 3:1 minimum.

━━━ RESPONSIVE BEHAVIOR ━━━
Desktop (≥1024px): Full-width bar, 64px height, generous horizontal padding (space.8).
Tablet (768-1023px): Same behavior but bar height reduces to 56px.
The bar is not designed for mobile (<768px) — not a mobile product at v1. If the screen is very small (e.g., 13" laptop at 125% scaling), the bar scales proportionally.

## SCREEN 2: CHAT CONTAINER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SCREEN: Chat Container — Route: N/A (overlay, expands from input bar)

━━━ PURPOSE ━━━
When the user needs a full conversation — reviewing past messages, asking follow-ups, exploring tool results — the chat container provides a complete chat interface. It expands from the input bar, creating a layered surface above the desktop.

━━━ VISUAL HIERARCHY ━━━
Priority order:
  1. Conversation header (conversation title, model indicator, close button) — top
  2. Message list (scrollable, newest at bottom) — primary content area
  3. Latest messages (at the visible scroll position) — what the eye processes first
  4. Input bar at bottom (persistent, always accessible)
  5. Sidebar toggle (left edge, conversation list — collapsed by default)

How achieved:
  → Size: container is 480px wide (fixed), height is 60% of screen height. Centered horizontally, anchored to bottom.
  → Color: bg.surface background, distinct from desktop behind the dimmed overlay.
  → Position: anchored to bottom, expands upward. Backdrop overlay dims the rest of the screen (overlay.backdrop at 50%).

━━━ COMPOSITIONAL INTENT ━━━
The chat container is a floating panel — not a full-screen app. The width is deliberately constrained (480px = comfortable reading width for body text). The backdrop overlay behind the container dims the desktop, signaling "the assistant IS the active context now." But the user's applications are still visible through the dim — this isn't a modal that blocks all awareness.

The container slides up from the input bar position (250ms, ease.enter). The input bar and chat container share the same input component at the bottom — there is no duplicate input. The input bar becomes the footer of the chat container.

The left sidebar (conversation list) is a collapsed rail. The user pulls it open with a drag handle or a toggle button. By default, the conversation occupies the full 480px width — the user sees their chat, not UI chrome.

└─ ChatContainer (480px wide, 60vh tall, bg.surface, radius.lg)
    ├─ Overlay (fixed, full screen, overlay.backdrop 50%)
    ├─ SidebarRail (collapsed, left edge, 16px wide strip with toggle button)
    │   └─ ToggleExpand (button, icon.md, "Show conversations")
    ├─ ChatPanel (flex-1)
    │   ├─ ConversationHeader (h3, conversation title, model badge)
    │   ├─ MessageList (flex-1, scrollable)
    │   │   ├─ MessageGroup (date separator)
    │   │   ├─ MessageBubble (per message)
    │   │   │   ├─ Avatar (small, icon-only for assistant, none for user)
    │   │   │   ├─ Content (body, text.primary, markdown rendered)
    │   │   │   ├─ Timestamp (body-sm, text.tertiary)
    │   │   │   └─ ToolCall (conditional inline card)
    │   │   │       ├─ Tool name + description
    │   │   │       ├─ Parameter display
    │   │   │       ├─ Run button (or "Approved" / "Denied" after action)
    │   │   │       └─ ExecutionResult (after run)
    │   │   └─ StreamingMessage (last item, real-time token rendering)
    │   └─ InputArea (footer, sticky bottom)
    │       ├─ InputField (body, text.primary)
    │       ├─ CharCounter (optional, body-sm, text.tertiary)
    │       └─ SendButton (icon.md)
    └─ SidebarExpanded (when open, 240px, slides from left)
        ├─ NewConversationButton
        ├─ ConversationList
        │   ├─ ConversationItem (title, truncated, date)
        │   └─ ...
        └─ SearchConversations (input, optional — v1 if time permits)

━━━ STATES ━━━

LOADING STATE (initial open, messages loading):
  Visual: Skeleton messages appear (3-4 shimmering message bubbles matching the expected shape). The input bar at the bottom is active and usable — users can start typing even while history loads.
  Duration: <500ms (conversations are local SQLite — fast). If network-dependent (cloud provider status check), the skeleton persists for provider status only.
  Copy: None. The skeleton IS the communication.

EMPTY STATE (new conversation, no messages yet):
  Visual: Empty message area with centered content:
    - A subtle icon or brand mark (icon.2xl, text.tertiary)
    - Empty state heading (h3, text.primary)
    - Empty state description (body, text.secondary)
    - Suggestion chips (3-4 example prompts) or the input bar at the bottom is the CTA
  Copy: [chat.empty.heading], [chat.empty.description], [chat.empty.suggestion_1], [chat.empty.suggestion_2], [chat.empty.suggestion_3].
  Psychological strategy: The empty state uses the Fresh Start Effect — it frames the new conversation as an opportunity, not a void. "What would you like to do?" paired with specific capability examples. The input bar at the bottom is visually dominant — the "action" is right there, one click away.

EMPTY STATE (sidebar — no previous conversations):
  Visual: "No conversations yet" with a subtle prompt: "Your first conversation will appear here."
  Copy: [sidebar.empty.heading], [sidebar.empty.description].

ERROR STATE (failed to load messages):
  Visual: Error banner at top of message list (bg.error-bg, border.error, body-sm) with retry button.
  Message: [error.chat.load_failed].
  Recovery: Retry button. If repeated failure, "Check your connection" or "Restart Ouroboros" suggestion.
  Edge case: Partial load (some messages loaded, some failed): the loaded messages are displayed, a separator line shows where the error occurred, and the error banner appears above that line.

ERROR STATE (stream disconnected mid-response):
  Visual: The partial message stays visible but grayed out with a subtle dashed-border frame. Error indicator below: "Response interrupted. [Retry]"
  Message: [error.chat.stream_interrupted].
  Recovery: Retry generates a complete new response. User keeps the partial context.

SUCCESS STATE (active conversation):
  Visual: Message list populated with user and assistant messages. User messages right-aligned (or have a subtle user indicator). Assistant messages left-aligned with a small assistant icon. Tool execution results shown as inline cards within the assistant message. Timestamps on hover.
  Micro-interactions:
    - New message slides in from bottom (200ms, ease.enter, translateY -8px → 0).
    - Tool execution card expands on click to show full details.
    - Streaming text renders token-by-token with a cursor indicator (subtle blinking pipe at the end of incomplete text).
    - Scroll-to-bottom button appears when the user scrolls up (40px circle, icon.sm, semi-transparent, bottom-right of message area).
    - When a new streaming message arrives and the user is scrolled up: a "New response" indicator appears at the bottom instead of auto-scrolling. Clicking it scrolls down.
  Progressive disclosure: The sidebar is hidden by default. Only the active conversation is visible. The user pulls the sidebar open when they want to switch conversations.

━━━ INTERACTIONS ━━━

Click conversation in sidebar: Switches to that conversation. Message list re-populates with a subtle crossfade (150ms).
Click "New conversation": Creates empty conversation. Sidebar closes (on mobile behavior) or stays open (desktop).
Type + Enter: Sends message. Loading state. Response streams.
Click tool "Run": Triggers permission dialog → execution → result.
Scroll up: Scroll-to-bottom button appears.
Click backdrop overlay: Closes chat container → input bar → bubble (200ms, ease.exit).
Escape: Same as backdrop click.
Resize handle: Bottom-right corner — user can resize chat container (min 380px wide, max 720px).
Drag container: User can move the container by dragging the header area.

Transition specifications:
  Entering: Input bar expands upward into chat container (250ms, ease.enter). Backdrop overlay fades in simultaneously (250ms, opacity 0 → 0.5).
  Leaving: Reverse — container collapses down to input bar (200ms, ease.exit), overlay fades out.
  Sidebar expand: Sidebar slides in from left (200ms, ease.enter, translateX -240px → 0).
  Sidebar collapse: Slides left (150ms, ease.exit, translateX 0 → -240px).

━━━ ACCESSIBILITY ━━━
Focus order: Input field first on open. Tab moves: Input → Send → conversation header actions → sidebar toggle → message list (arrow keys to navigate messages) → back to input.
ARIA:
  - Message list: role="log", aria-live="polite" (announces new messages)
  - Streaming message: aria-live="assertive" (announces each meaningful chunk, not every token)
  - Input: aria-label="Message"
  - Sidebar toggle: aria-expanded="true/false"
Keyboard shortcuts:
  - Ctrl+N: New conversation
  - Ctrl+K: Search conversations
  - Escape: Close chat
  - Arrow Up in input: Edit last message
Screen reader: Should narrate messages in order. Tool calls announced as "Assistant suggests running [tool name]" with the tool description. Results announced as "[tool name] completed" with a brief result summary.
Focus trap: When chat container is open, focus stays within it (Tab cycles through container elements, Shift+Tab goes backward).

━━━ RESPONSIVE BEHAVIOR ━━━
Desktop (≥1024px): Default layout — 480px wide, centered, 60vh tall.
Laptop (768-1023px): Container width reduces to 420px. Sidebar collapses to icon-only rail (shows only icons, no text labels) when screen is tight.
Small screens (<768px): Container becomes full-width, full-height (80vh) anchored to bottom. This is essentially "the chat app fills the screen" — appropriate for small laptops.
On very large screens (≥2560px): Container stays at 480px. Doesn't scale up proportionally — reading comfort is the constraint, not screen real estate.

## SCREEN 3: PERMISSION DIALOG
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SCREEN: Permission Dialog — Route: N/A (modal overlay)

━━━ PURPOSE ━━━
Before the assistant executes a tool on the user's machine (especially destructive or sensitive operations), the user must explicitly approve. This dialog presents what the tool will do, what it will access, and lets the user approve, deny, or set a default.

━━━ VISUAL HIERARCHY ━━━
Priority order:
  1. Dialog title — "Allow [tool name]?" (h2, text.primary)
  2. Tool description + what it will access (body, text.primary)
  3. Action details — the specific command or operation (mono, bg.surface, bordered)
  4. Risk level indicator (color-coded badge: safe / caution / destructive)
  5. Action buttons: "Allow once" (primary), "Deny" (secondary), "Always allow" (tertiary)

└─ PermissionDialog (modal, 380px wide, centered, Level 3 elevation)
    ├─ Backdrop (overlay.backdrop 50%)
    ├─ DialogHeader (tool icon + tool name + risk badge)
    ├─ DialogBody
    │   ├─ Description (what this tool does)
    │   ├─ CommandPreview (the actual command that will run, mono)
    │   └─ AccessList (files/directories/resources affected)
    ├─ DialogFooter
    │   ├─ AllowOnceButton (primary, bg.brand)
    │   ├─ DenyButton (secondary, bg.surface, border.default)
    │   └─ AlwaysAllowCheckbox (label-sm, text.tertiary)
    └─ RememberOption ("Don't ask again for [tool name]" — sets default)

━━━ STATES ━━━

LOADING STATE:
  N/A — permission dialogs appear instantly (no data to fetch).

EMPTY STATE:
  N/A — dialog has content or it doesn't appear.

ERROR STATE:
  Visual: If the tool description or parameters fail to parse, the dialog shows a simplified version with a warning: "This tool's description couldn't be loaded. Proceed with caution."
  Copy: [permission.error.unclear_tool].

SUCCESS STATE:
  Visual: Full dialog as described. The dialog animates in: scales from 0.95 to 1 (200ms, ease.enter) with simultaneous opacity 0 → 1.
  After approval: Dialog closes (150ms, ease.exit). The tool execution begins and the result appears in the chat.
  After denial: Dialog closes (150ms, ease.exit). A "Denied" indicator appears in the chat where the tool call was.
  Micro-interactions: The "Allow once" button has a subtle glow on hover (box-shadow with brand.400). Deny button dims slightly on hover. Checkbox has a smooth toggle animation (150ms).

━━━ INTERACTIONS ━━━
  Click "Allow once": Tool executes this time only.
  Click "Always allow": Tool executes now, and permission default changes to "allow" for this tool. User can undo in Settings.
  Click "Deny": Tool does not execute. Permission state recorded as "denied this time."
  Click backdrop: Same as "Deny."
  Escape: Same as "Deny."

━━━ ACCESSIBILITY ━━━
Focus order: Allow once button auto-focused. Tab: Allow once → Always allow checkbox → Deny → back to Allow.
ARIA: Dialog has role="dialog", aria-modal="true", aria-labelledby="permission-title".
Focus trap: Yes — focus stays within the dialog. Escape closes (denies).
Screen reader: Announces "Permission required: [tool name] wants to [action]. Allow or deny?"

━━━ RESPONSIVE BEHAVIOR ━━━
Desktop: 380px wide, centered.
Small screens: Dialog becomes full-width (90vw) anchored to bottom of screen. Buttons stack vertically instead of horizontally.

## SCREEN 4: SETTINGS PANEL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SCREEN: Settings Panel — Route: N/A (modal panel)

━━━ PURPOSE ━━━
The user configures models, API keys, permissions, appearance, and general preferences. Settings is accessed from the bubble right-click menu or from the chat container header.

━━━ VISUAL HIERARCHY ━━━
Priority order:
  1. Settings navigation tabs (left sidebar: General, Models, Providers, Permissions)
  2. Active tab content (right panel)
  3. Save/close actions (bottom-right)

└─ SettingsPanel (600px wide, 70vh tall, centered, modal)

SCREEN: Onboarding — Route: N/A (first-run flow)

━━━ PURPOSE ━━━
On first install, the flow gets the user from "app launched" to "first response received" in under 2 minutes. The onboarding is minimal — it detects hardware, downloads a model if needed, and guides the user to their first interaction.

━━━ VISUAL HIERARCHY ━━━
Priority order:
  1. Welcome screen — brand mark + "Ouroboros is ready" (h1)
  2. Hardware check result — "Your computer can run [model name]" (body)
  3. Continue button (or auto-advance)

The onboarding has exactly 2-3 steps, not 5-7. Every step after the first is optional (user can skip).

└─ OnboardingOverlay (full screen, bg.page)
    ├─ Step 1: Welcome
    │   ├─ Brand mark (animated bubble preview)
    │   ├─ Headline (h1, DM Serif Display)
    │   ├─ Tagline (body-lg, text.secondary)
    │   └─ "Get started" button (primary)
    ├─ Step 2: Hardware (auto-detects, shows result)
    │   ├─ GPU detected: "NVIDIA RTX 3060 — 12GB VRAM"
    │   ├─ Recommended model: pre-selected
    │   ├─ Download now / Skip (use cloud) options
    │   └─ Progress bar (if downloading)
    └─ Step 3: Ready
        ├─ "You're all set" (h2)
        ├─ The bubble appears on the desktop
        ├─ "Click me to get started" label pointing to bubble
        └─ Dismisses when user clicks the bubble

━━━ STATES ━━━

LOADING STATE (hardware detection):
  Visual: Animated radar/pulse graphic scanning hardware. "Checking your computer..." label.
  Duration: 2-5 seconds. Should feel fast.

EMPTY STATE: N/A — onboarding IS the empty state experience.

ERROR STATE (hardware insufficient):
  Visual: "Your computer may struggle with local models." Explanation of minimum requirements. Option to use cloud models instead. "You can still use Ouroboros with cloud providers."
  Copy: [onboarding.error.low_specs].

ERROR STATE (model download failed):
  Visual: "Download didn't complete. You can try again or skip to cloud models."
  Recovery: Retry button or Skip button.

SUCCESS STATE: User reaches Step 3 and the bubble is active.

━━━ INTERACTIONS ━━━
  All steps: Forward navigation only (not back — this is a one-time flow, not a config wizard). User can skip any step.
  Download step: Progress bar, cancel button.
  Final step: CTA is "click the bubble" — not a button. The bubble is the interactive element.

━━━ ACCESSIBILITY ━━━
  Focus: Forward through steps in order. Keyboard: Enter to advance.
  Screen reader: Reads each step's content. Announces hardware detection result.
  Reduced motion: Animations are simplified (fade instead of slide).
