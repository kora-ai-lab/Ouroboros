BRIEF — Ouroboros
Generated by Ophidian · Phase 0

━━━ ONE SENTENCE ━━━
A local-first desktop AI assistant that lives as a floating bubble on your screen, executes any task a human can do with a computer, and evolves its own capabilities over time — without ever leaving your workflow.

━━━ PROBLEM SOLVED ━━━
Current AI assistants trap users inside chat apps, browser tabs, or terminal windows, forcing constant context switching. CLI tools (Claude Code, openclaw) require technical skill and command-line comfort. Browser-based assistants don't have OS access. Users toggle between their work and their AI, which kills flow state and wastes cognitive energy. The assistant should come to the user — not the reverse.

━━━ JOB-TO-BE-DONE ━━━
"When I'm working on my computer and need an answer, a file edited, content generated, or a task automated, I want to summon my assistant instantly without leaving my current app, so that I can stay in flow and get the result without breaking context."

━━━ TARGET ━━━
Primary user: Professionals, creators, and everyday computer users who want AI assistance without technical friction. They currently use ChatGPT/Claude in a browser tab, or tolerate CLI tools if they're developers. Their frustration: switching windows to ask a question, then switching back — dozens of times per day. Their current workaround: keeping an AI chat in a pinned browser tab and Alt-Tabbing constantly.

Secondary user: Developers and power users who want deep OS integration, sandboxed execution, and a self-evolving toolset. Currently using Claude Code, Copilot, or openclaw, but frustrated by cost, cloud dependence, or security gaps.

━━━ MVP SCOPE (80/20 FILTERED) ━━━
1. **Floating bubble UI + chat container** — the one thing that, if it works, delivers 80% of value: summon the assistant from anywhere with a click or global hotkey, type a request, get a response, return to work. No window management. No context switch.
2. **Local AI inference (llama.cpp)** — private, offline, zero-latency chat for the free tier. This is the trust anchor. Users know their data never leaves the machine for local queries.
3. **Sandboxed tool execution engine** — enables the assistant to actually DO things: read/write files, run commands, create and install new tools. This is the self-evolving core that differentiates Ouroboros from every chat-only assistant.

Explicitly NOT in v1:
→ Cloud model orchestration (paid tier) — deferred because local AI + tool execution alone proves the value proposition. Cloud tier is monetization, not MVP function.
→ Self-evolving tool creation — deferred because the sandboxed execution engine is the prerequisite. v1 ships the engine; v2 ships the recursive tool-builder that uses it.
→ Multimodal generation (image/video) — deferred because text-based task execution is the 80/20 core. Media generation is a v2 expansion.
→ Enterprise licensing — deferred until v1 proves product-market fit. Build for individuals first.

━━━ DIFFERENTIATION ━━━
Every other assistant makes the user come to it (open a tab, launch a terminal, switch windows). Ouroboros comes to the user — it's always one click away, floating on top of any app. The floating bubble is not a gimmick; it's the structural advantage that eliminates context switching. The sandboxed tool execution engine is the second differentiator: other assistants can chat; Ouroboros can ACT on the user's machine, and eventually build its own tools.

━━━ CONSTRAINTS ━━━
Target: No deadline — quality over speed. First functional prototype within 4-6 weeks.
Devices: Desktop — Windows, macOS, Linux. No mobile at v1.
Languages: English (user-facing). Code/tools are language-agnostic.
Compliance: GDPR, end-user security (zero-config, safe by default). Must protect non-technical users from prompt injection, file system damage, and credential leaks.

━━━ SUCCESS AT D+30 ━━━
At least 100 daily active users completing ≥3 assistant interactions each, with <2% uninstall rate. Net Promoter Score ≥ 50 from first 50 users.

━━━ ASSUMPTIONS REQUIRING VALIDATION ━━━
[ASSUMPTION: Users will tolerate running a local LLM on their hardware — inference speed and resource usage must be acceptable on consumer laptops (8GB RAM).]
[ASSUMPTION: The floating bubble UI pattern is intuitive, not annoying — users won't perceive it as bloatware or dismiss/disable it permanently.]
[ASSUMPTION: Sandboxed execution is technically feasible with sufficient safety guarantees for non-technical users — the permission model must prevent "assistant deleted my files" disasters without requiring user configuration.]
[ASSUMPTION: There is sufficient demand for a local-first desktop assistant beyond developers — non-technical users actually WANT OS-level AI, not just a better chat app.]
[ASSUMPTION: puter.js and Pollinations BYOK are viable, stable dependencies for the free tier's cloud augmentation — they won't introduce breaking changes or shutdown mid-development.]
